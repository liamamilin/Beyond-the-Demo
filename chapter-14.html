当开发者构建小型程序时，他们通常假设操作会成功。输入是正确的，服务会响应，系统会不间断地完成工作。

这种假设在受控环境中很好用。在开发过程中，开发者经常自己提供输入，在本地运行程序，并直接观察结果。

然而，一旦软件开始在真实环境中运行，一种不同的现实就浮现出来。

网络变得不可靠。外部服务响应缓慢或完全失败。用户提供意外的输入。数据库经历临时中断。

换句话说，失败不是异常——它是真实系统的正常条件。

专业软件因此采纳了一种根本不同的思维方式。它不是为成功而设计、对失败做出反应，而是将失败作为默认场景来设计。

这种转变将错误处理从事后补充转变为系统架构的基本组成部分。

15.1 验证：防止无效状态（Validation: Preventing Invalid States）

防止失败的最早机会之一是输入验证（input validation）。

每当系统从外部源接收信息时——无论是通过 API 请求、命令行参数还是用户界面——它必须验证输入是否满足预期的约束。

验证确保必填字段存在、值遵循正确的格式、输入之间的关系保持一致。

没有验证，无效数据可能进入系统，并在处理过程的后期造成不可预知的行为。错误可能出现在远离其原始原因的地方，使诊断变得困难。

专业系统因此尽可能早地执行验证。

通过立即拒绝无效输入，它们防止系统进入不稳定状态，并向用户提供关于需要纠正什么的清晰反馈。

15.2 重试：处理临时性失败（Retry: Handling Temporary Failures）

并非所有失败都代表永久性问题。

许多错误是由于临时条件造成的。网络请求可能超时，服务可能短暂不可用，数据库可能经历瞬时负载。

在这些情况下，重试操作通常就能成功。

专业系统识别出这种模式，并为与外部依赖交互的操作实现重试机制（retry mechanisms）。

重试策略通常包含限制和延迟。系统在短暂间隔后再次尝试操作，在报告失败前重复尝试定义的次数。

这种方法允许系统从临时性问题中自动恢复，无需人工干预。

目标不是消除所有失败，而是减少临时中断的影响。

15.3 降级：维持功能（Fallback: Maintaining Functionality）

有时即使在重试后，操作也不能成功。

在这些情况下，系统可能通过切换到替代路径来提供部分功能。这种策略被称为降级（fallback）。

降级机制允许系统在降级但可用的状态下继续运行。

例如，一个无法连接到其主数据库的系统可能切换到本地缓存。一个无法获取实时数据的组件可能提供最后一次已知良好的结果。一个依赖于外部服务的功能可能返回一个合理的默认值。

降级确保系统不会因为一个组件的失败而完全停止工作。

用户可能体验稍微降低的功能，但核心系统保持可用。

15.4 优雅地沟通错误（Communicating Errors Gracefully）

当失败发生时，系统如何与用户沟通对信任有显著影响。

练手项目经常以对用户不友好的方式呈现错误：技术性的堆栈跟踪、通用的”出了点问题”消息，或完全没有反馈。

专业系统提供清晰、可操作的信息。一个好的错误消息回答三个问题：

出了什么问题？ 一个对用户友好的描述，解释失败的性质。

为什么出问题？ 上下文帮助用户理解导致失败的原因。

下一步该做什么？ 关于如何解决或缓解问题的具体指导。

通过将错误转化为有用的沟通，专业保护了用户的信心。

15.5 前瞻性错误与运行时错误（Expected vs. Unexpected Errors）

并非所有错误都是平等的。专业系统区分两种不同的错误类别：

前瞻性错误（expected errors）是系统已经预见并为其设计了处理方式的错误。无效输入、缺失资源和认证失败都属于这一类别。这些错误应该被优雅地处理，并转化为清晰的消息。

运行时错误（unexpected errors）是系统未预见的错误。空指针异常、连接意外断开和编程错误属于这一类别。这些错误应该被记录，然后以可控的方式失败，而不是让系统处于不一致的状态。

经过良好测试的系统其运行时错误会较少，但它们仍然为失败做好了准备。

15.6 实践指南：错误处理模式

以下是在整个系统中应用的简单错误处理模式。

# 验证
def create_user(data):
    if not data.get("email"):
        return {"error": "EMAIL_REQUIRED", "message": "邮箱是必填项"}

# 重试
def call_with_retry(service_call, max_retries=3):
    for attempt in range(max_retries):
        try:
            return service_call()
        except TemporaryError:
            if attempt == max_retries - 1:
                raise
            time.sleep(1 * (attempt + 1))

# 降级
def fetch_user_profile(user_id):
    try:
        return database.fetch(user_id)
    except DatabaseError:
        return cache.get(user_id)  # 降级到缓存

15.7 小结

在真实系统中，失败是不可避免的。专业软件不是通过假装失败不会发生来构建的，而是通过设计对失败的鲁棒性来构建的。

通过验证、重试、降级和清晰的沟通，开发者创建了不仅能优雅地处理问题、还能在问题出现时保持用户信心的系统。

真正的专业标志不是系统是否失败，而是当失败发生时，系统做了什么。下一章，我们将探讨测试——如何让系统不仅运行，而且可以信任。
