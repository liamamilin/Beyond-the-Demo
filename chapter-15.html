在项目的早期阶段，开发者通常依赖一种简单的验证形式：运行程序，观察它是否产生预期的结果。

如果输出看起来正确，系统就被认为在工作。

对于练手项目来说，这种方法通常足够了。开发者理解代码，系统很小，环境是受控的。

然而，随着软件的增长并开始随时间演化，这种非正式的验证变得不可靠。一个改进了一个功能的改动可能无意中破坏了另一个功能。一个小重构可能引入难以手动检测的微妙错误。

专业系统通过测试（testing）来解决这个问题。

测试将系统的行为转化为一组可重复的检查。开发者不是依赖记忆或直觉，而是使用自动化测试来验证关键功能在系统变化时继续工作。

这种转变是从实验性到可靠性的演化过程中的重要一步。

16.1 测试为什么重要（Why Tests Matter）

测试提供两个基本好处。

首先，它创造信心（confidence）。开发者可以修改系统而不必一直担心隐藏的问题会出现。当测试通过时，它们充当了系统仍然按预期行为的证据。

其次，测试充当活的文档（living documentation）。每个测试都演示了系统特定部分应该如何行为。新开发者可以阅读测试来理解软件的预期行为。

通过这种方式，测试不仅保护系统免受回归，还澄清了它的设计。

没有测试，验证行为的唯一可靠方式就是手动运行整个应用程序。随着系统增长，这种方法变得不切实际。

16.2 单元测试（Unit Tests）

单元测试关注系统的最小部分。

一个单元测试通常隔离地检查单个函数、类或模块。通过控制输入和观察输出，测试验证组件在特定条件下正确行为。

因为单元测试隔离了单个组件，它们运行快速，并且当失败发生时易于诊断。

它们允许开发者确认系统的基本构建块按预期行为。

然而，仅靠单元测试不能保证不同组件之间正确交互。

16.3 契约测试（Contract Tests）

契约测试检查组件之间的约定。

每当系统的两个部分通信时——比如客户端调用 API，或一个服务与另一个服务交互——它们依赖关于数据格式和行为的共享预期。

契约测试验证这些预期是否保持有效。

例如，如果 API 承诺为特定请求返回特定结构，契约测试确保即使内部实现演化，结构也保持一致。

这些测试保护组件之间的边界，防止微妙的集成问题意外出现。

16.4 端到端测试（End-to-End Tests）

端到端测试验证系统作为一个整体是否工作。

与测试单个组件或它们之间的接口不同，端到端测试运行完整的用户场景。它们测试系统的所有层——从接口到核心逻辑到存储。

这些测试提供了最高级别的信心，证明系统作为一个整体正常运行。

然而，它们也运行最慢，当失败发生时诊断起来最困难。它们通常保留用于最关键的用户路径。

专业系统通常将测试组织为一个金字塔：许多快速的单元测试在底部，中等数量的契约测试在中间，少数关键的端到端测试在顶部。

16.5 测试驱动开发（Test-Driven Development）

一种常见的专业实践是测试驱动开发（TDD, Test-Driven Development）。

在 TDD 中，开发者在写生产代码之前先编写测试。这翻转了传统的开发顺序：测试首先定义系统应该做什么，然后代码被编写来使测试通过。

这种方法有几个好处：

  • 它迫使开发者考虑接口和预期行为，然后再考虑实现细节
  • 它确保代码从一开始就是可测试的
  • 它创建了一个正在进行的回归测试套件

虽然 TDD 不是在所有情况下都是必要的，但对于逻辑复杂的模块来说，它特别有价值。

16.6 实践指南：开始测试

16.6.1 测试检查清单

开始使用测试时，关注这些领域：

核心逻辑： - [ ] 核心功能的最重要单元测试到位了吗？ - [ ] 边界情况（空值、最大值、无效输入）被覆盖了吗？

关键路径： - [ ] 应用的关键用户路径被端到端测试覆盖了吗？ - [ ] 错误场景被测试了吗？

回归保护： - [ ] 修复的 bug 是否有一个防止它重新出现的测试？ - [ ] 测试会在不相关的变更上失败吗（脆弱的测试）？

16.7 小结

测试将软件从”可能能运行”转变为”可证明工作”。它将验证过程从手动检查转变为自动化的、可重复的检查。

虽然测试需要额外的工作，但它通过预防问题来节省未来的时间，并给予开发者进行更改的信心。

在专业系统中，测试不是可选的。它是工程过程的基本组成部分。
