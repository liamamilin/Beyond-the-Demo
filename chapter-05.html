在最深层次上，软件是简单的。它由三个基本元素组成：

对象（Objects）+ 动作（Actions）+ 状态（States）

这个三元组代表了软件的本质：软件通过动作操_作对象，随着时间的推移改变它们的状态。代码库中的每一个函数、类、变量都映射到这三个概念之一。

当开发者理解了这个哲学之后，命名就变得简单了：

  • 对象用名词（nouns）命名：Transaction、Account、User、Order
  • 动作用动词（verbs）命名：create、update、validate、process
  • 状态用形容词或状态名词命名：active、pending、complete、isDeleted、hasPermission”

这个简单的框架消除了大多数命名不确定性。开发者不再问”我应该把它叫什么？“，而是问”这代表什么：对象、动作还是状态？”

练手项目和专业系统的区别，往往始于这个问题。练手项目任意命名。专业系统有意地命名，以对象-动作-状态（Object-Action-State）哲学作为基础。

本章探讨如何系统化地应用这个哲学，构建一套完整、连贯的命名词汇。

6.1 对象-动作-状态哲学（The Object-Action-State Philosophy）

每一段软件都可以通过这个三元组来理解。一个系统通过执行动作来处理对象，改变它们的状态。

考虑一个电商应用：

  • 对象：ShoppingCart、Product、PaymentMethod、CustomerProfile
  • 动作：addToCart()、processPayment()、calculateTotal()、validateInventory()
  • 状态：cartEmpty、paymentPending、inventoryAvailable、userAuthenticated

这些名称不是任意的。它们直接表达了每个组件在系统领域模型中所代表的内容。

当命名遵循这个框架时，代码变得自我文档化（self-documenting）。开发者读到 cart.processPayment() 时会立刻理解：一个 cart 对象（名词）正在经历支付流程（动词），这会推动 cart 的状态从一种变为另一种。

这种清晰来自对简单命名哲学的系统应用，而不是来自大量的注释或文档。

6.2 对象命名系统（Object Naming System）

对象是软件中的名词。它们代表系统中存在的事物：数据实体、概念、具有身份和行为的结构。

专业系统区分几种类型的对象，每种都有其命名约定。

6.2.1 实体（Entities）

实体是具有身份和生命周期的对象。它们代表领域中的核心概念：

  • Customer、Order、Product、Invoice、Account
  • Session、Transaction、Subscription、Membership

实体名称应该是单数名词，清晰地指示对象代表什么。它们捕捉领域概念的本质。

6.2.2 值对象（Value Objects）

值对象代表没有独立身份的值或度量。它们由其属性定义：

  • EmailAddress、Money、Address、PhoneNumber
  • Color、Coordinate、Duration、Percentage

值对象名称描述它们代表什么，强调其值的本质而非身份。

6.2.3 服务（Services）

服务代表不属于特定实体的操作或能力：

  • PaymentProcessor、EmailService、AuthenticationProvider、NotificationService
  • DataValidator、FileExporter、CacheManager、RateLimiter

服务名称通常以能力描述符结尾，如 Processor、Service、Provider 或 Manager，清晰地指示该对象提供功能而非代表数据。

这些对象类型之间的区分很重要，因为它防止了代码库中的混淆。当开发者看到 EmailAddress，他们立刻理解这是一个值对象。当看到 EmailService，他们知道这提供邮件功能。

这种清晰度让系统的领域语言自然地从事命名选择中浮现出来。

6.3 动作命名系统（Action Naming System）

动作是软件中的动词。它们代表系统做什么：操作、转换、以及操纵对象或改变状态的行为。

专业系统将动作分为四种不同的类别，每种都有特定的命名模式。

6.3.1 命令动作（Command Actions）

命令动作执行状态变更或副作用。它们修改系统：

  • createUser()、updateProfile()、deleteAccount()、archiveRecord()
  • sendEmail()、processPayment()、publishArticle()、expireSession()

命令名称使用强动词，清晰地指示正在执行的动作。它们通常遵循 verbObject() 的模式，其中动词描述发生了什么，对象描述了影响什么。

6.3.2 查询动作（Query Actions）

查询动作在不改变状态的情况下检索信息。它们向系统询问问题：

  • getUserById()、findOrdersByDate()、getAvailableInventory()、calculateTotal()
  • searchProducts()、fetchProfile()、listSubscriptions()、validateCredentials()

查询名称使用强调检索或计算的动词：get、find、fetch、list、search、calculate、validate。这些名称清晰地表明函数返回信息而非修改状态。

6.3.3 布尔动作（Boolean Actions）

布尔动作返回 true/false 答案。它们测试条件：

  • isValid()、hasPermission()、canEdit()、isAuthenticated()
  • exists()、isEmpty()、isComplete()、hasAccess()

布尔动作名称通常以 is、has、can 或类似的疑问动词开头。这个命名约定立即表明返回值是布尔值，使代码更可读、更可预测。

6.3.4 转换动作（Conversion Actions）

转换动作将一种类型的对象转换为另一种：

  • toDTO()、toEntity()、toJson()、toString()
  • convertToCurrency()、mapToView()、serialize()、deserialize()

转换名称使用表示转换的动词：to、convert、map、serialize、transform。它们显式地展示源类型和目标类型，使转换过程透明。

通过这样分类动作，开发者仅从名称就能立即理解任何函数或方法的本质。这消除了歧义，使代码库更可预测、更可维护。

6.4 状态命名系统（State Naming System）

状态是软件中的形容词和状态名词。它们代表描述对象或系统的条件、阶段和属性。

专业系统使用四种主要的模式来命名状态，取决于所代表条件的类型。

6.4.1 布尔状态（Boolean States）

布尔状态代表简单的 true/false 条件：

  • isActive、isDeleted、isVisible、isPublished
  • hasPermission、hasSubscription、hasAccess、isVerified

布尔状态名称通常使用 is 或 has 前缀，使布尔性质一目了然。这些名称是自我文档化的：if (user.isActive) 读起来像自然语言。

6.4.2 枚举状态（Enumeration States）

枚举状态代表不同的阶段或类别：

  • OrderStatus：pending、processing、shipped、delivered、cancelled
  • UserStatus：active、inactive、suspended、deleted
  • PaymentStatus：authorized、captured、refunded、failed

枚举名称使用清晰、描述性的术语来代表可能的状态。它们避免技术术语，使用领域相关的语言：shipped 而非 state_3。

6.4.3 数值状态（Numerical States）

数值状态代表可测量的数量或计数器：

  • retryCount、remainingAttempts、totalAmount、balance
  • priorityLevel、versionNumber、timestamp、duration

数值状态名称描述数字代表什么，而不是简单地叫它 count 或 value。名称提供了上下文：retryCount 清晰地表明这是计算重试次数，而不是别的东西。

6.4.4 复合状态（Composite States）

复合状态结合多条信息：

  • shippingAddress、billingProfile、contactInformation
  • paymentDetails、subscriptionPlan、userPreferences

复合状态名称使用名词短语将相关属性分组在一起。它们为相关数据创建自然的容器，使代码更有组织，关系更清晰。

当状态命名遵循这些模式时，阅读代码变得直观。if (order.status === OrderStatus.shipped) 立即告诉你你在检查什么，不需要查阅文档或解码晦涩的状态名。

6.5 命名框架应用指南

好的命名来自系统的哲学。对象-动作-状态框架为一致的命名决策提供了基础。

第一步：识别类别

对每一个你创建的标识符，问：这是一个对象、一个动作，还是一个状态？

# 示例：分析代码元素
user              # 对象（实体）
processPayment()  # 动作（命令）
isActive          # 状态（布尔）
UserStatus        # 对象（枚举）
calculateTotal()  # 动作（查询）
retryCount        # 状态（数值）

第二步：应用适当的模式

  • 对象：使用单数名词，区分实体/值对象/服务，选择领域相关术语
  • 动作：使用强动词，分类为命令/查询/布尔/转换，遵循类型命名约定
  • 状态：使用形容词或描述性名词，清晰指示状态类型（布尔/枚举/数值/复合）

第三步：一致性检查

  • 所有实体使用单数、领域相关的名词
  • 值对象描述其值的本质
  • 服务以能力描述符结尾（Service、Processor、Manager）
  • 没有通用名称（data、info、item、thing）

命名评审流程：

三秒测试 — 你能在三秒内理解名称代表什么吗？如果不能，名称需要改进。

对象-动作-状态映射 — 对每个标识符，验证它清晰地属于三个类别之一。

一致性检查 — 相似概念在代码库中命名一致吗？对同一想法各处使用相同的术语吗？

6.6 命名最佳实践总结

原则 描述 示例
具体 避免通用术语，使用领域特定语言 Transaction vs Data
一致 对同一概念使用相同术语 始终使用 create，不要混用 create、make、build
需要时详细 更长更清晰的名称胜过简短的歧义名称 calculateOrderTotal vs calc

6.7 小结

对象-动作-状态哲学为软件中的命名提供了系统化的基础。代码库中的每一个元素都可以被理解为代表一个对象（名词）、一个动作（动词）或一个状态（形容词/名词）。

通过一致地应用这个框架，开发者创建了一门连贯的领域语言，使代码自我文档化且直观。对象根据其类型（实体、值对象、服务）命名。动作根据其性质分类（命令、查询、布尔、转换）。状态根据其类别区分（布尔、枚举、数值、复合）。

这种系统化方法消除了任意的命名决策，创造了一个揭示系统结构和意图的词汇表。结果是代码读起来像自然语言，开发者可以直接从名称中理解关系和职责。

从随意命名到系统化命名的转变，是区分练手项目与专业系统的那些安静但强大的转变之一。

实践建议：

  1. 从分类开始：在命名任何东西之前，先确定它是对象、动作还是状态。
  2. 构建领域词汇表：记录定义系统领域的核心名词、动词和形容词。
  3. 审查一致性：定期审计你的代码库，确保相同的术语被一致地使用。

立即行动：

选择你项目中的一个模块，系统化地审查所有标识符。将每个分类为对象、动作或状态，并验证命名遵循相应的模式。重命名任何不符合框架的标识符。

## 动作命名系统（Action Naming System）

动作是软件中的动词。它们代表系统做什么：操作、转换、以及操纵对象或改变状态的行为。

专业系统将动作分为四种不同的类别，每种都有特定的命名模式。

### 命令动作（Command Actions）

命令动作执行状态变更或副作用。它们修改系统：

- `createUser()`、`updateProfile()`、`deleteAccount()`、`archiveRecord()`
- `sendEmail()`、`processPayment()`、`publishArticle()`、`expireSession()`

命令名称使用**强动词**，清晰地指示正在执行的动作。它们通常遵循 `verbObject()` 的模式，其中动词描述发生了什么，对象描述了影响什么。

### 查询动作（Query Actions）

查询动作在不改变状态的情况下检索信息。它们向系统询问问题：

- `getUserById()`、`findOrdersByDate()`、`getAvailableInventory()`、`calculateTotal()`
- `searchProducts()`、`fetchProfile()`、`listSubscriptions()`、`validateCredentials()`

查询名称使用强调检索或计算的动词：`get`、`find`、`fetch`、`list`、`search`、`calculate`、`validate`。这些名称清晰地表明函数返回信息而非修改状态。

### 布尔动作（Boolean Actions）

布尔动作返回 true/false 答案。它们测试条件：

- `isValid()`、`hasPermission()`、`canEdit()`、`isAuthenticated()`
- `exists()`、`isEmpty()`、`isComplete()`、`hasAccess()`

布尔动作名称通常以 `is`、`has`、`can` 或类似的疑问动词开头。这个命名约定立即表明返回值是布尔值，使代码更可读、更可预测。

### 转换动作（Conversion Actions）

转换动作将一种类型的对象转换为另一种：

- `toDTO()`、`toEntity()`、`toJson()`、`toString()`
- `convertToCurrency()`、`mapToView()`、`serialize()`、`deserialize()`

转换名称使用表示转换的动词：`to`、`convert`、`map`、`serialize`、`transform`。它们显式地展示源类型和目标类型，使转换过程透明。

通过这样分类动作，开发者仅从名称就能立即理解任何函数或方法的本质。这消除了歧义，使代码库更可预测、更可维护。

## 状态命名系统（State Naming System）

状态是软件中的形容词和状态名词。它们代表描述对象或系统的条件、阶段和属性。

专业系统使用四种主要的模式来命名状态，取决于所代表条件的类型。

### 布尔状态（Boolean States）

布尔状态代表简单的 true/false 条件：

- `isActive`、`isDeleted`、`isVisible`、`isPublished`
- `hasPermission`、`hasSubscription`、`hasAccess`、`isVerified`

布尔状态名称通常使用 `is` 或 `has` 前缀，使布尔性质一目了然。这些名称是自我文档化的：`if (user.isActive)` 读起来像自然语言。

### 枚举状态（Enumeration States）

枚举状态代表不同的阶段或类别：

- `OrderStatus`：`pending`、`processing`、`shipped`、`delivered`、`cancelled`
- `UserStatus`：`active`、`inactive`、`suspended`、`deleted`
- `PaymentStatus`：`authorized`、`captured`、`refunded`、`failed`

枚举名称使用清晰、描述性的术语来代表可能的状态。它们避免技术术语，使用领域相关的语言：`shipped` 而非 `state_3`。

### 数值状态（Numerical States）

数值状态代表可测量的数量或计数器：

- `retryCount`、`remainingAttempts`、`totalAmount`、`balance`
- `priorityLevel`、`versionNumber`、`timestamp`、`duration`

数值状态名称描述数字代表什么，而不是简单地叫它 `count` 或 `value`。名称提供了上下文：`retryCount` 清晰地表明这是计算重试次数，而不是别的东西。

### 复合状态（Composite States）

复合状态结合多条信息：

- `shippingAddress`、`billingProfile`、`contactInformation`
- `paymentDetails`、`subscriptionPlan`、`userPreferences`

复合状态名称使用名词短语将相关属性分组在一起。它们为相关数据创建自然的容器，使代码更有组织，关系更清晰。

当状态命名遵循这些模式时，阅读代码变得直观。`if (order.status === OrderStatus.shipped)` 立即告诉你你在检查什么，不需要查阅文档或解码晦涩的状态名。

## 命名框架应用指南

好的命名来自系统的哲学。对象-动作-状态框架为一致的命名决策提供了基础。

**第一步：识别类别**

对每一个你创建的标识符，问：这是一个对象、一个动作，还是一个状态？

```python
# 示例：分析代码元素
user              # 对象（实体）
processPayment()  # 动作（命令）
isActive          # 状态（布尔）
UserStatus        # 对象（枚举）
calculateTotal()  # 动作（查询）
retryCount        # 状态（数值）
```

**第二步：应用适当的模式**

- **对象**：使用单数名词，区分实体/值对象/服务，选择领域相关术语
- **动作**：使用强动词，分类为命令/查询/布尔/转换，遵循类型命名约定
- **状态**：使用形容词或描述性名词，清晰指示状态类型（布尔/枚举/数值/复合）

**第三步：一致性检查**

- 所有实体使用单数、领域相关的名词
- 值对象描述其值的本质
- 服务以能力描述符结尾（Service、Processor、Manager）
- 没有通用名称（data、info、item、thing）

**命名评审流程：**

**三秒测试** — 你能在三秒内理解名称代表什么吗？如果不能，名称需要改进。

**对象-动作-状态映射** — 对每个标识符，验证它清晰地属于三个类别之一。

**一致性检查** — 相似概念在代码库中命名一致吗？对同一想法各处使用相同的术语吗？

## 命名最佳实践总结

| 原则 | 描述 | 示例 |
|------|------|------|
| **具体** | 避免通用术语，使用领域特定语言 | `Transaction` vs `Data` |
| **一致** | 对同一概念使用相同术语 | 始终使用 `create`，不要混用 `create`、`make`、`build` |
| **需要时详细** | 更长更清晰的名称胜过简短的歧义名称 | `calculateOrderTotal` vs `calc` |
| **避免缩写** | 只使用行业标准缩写 | `URL`、`ID` 可以；`usr`、`pwd` 不行 |
| **使用肯定表述** | 尽可能避免否定 | `isValid` vs `isNotInvalid` |
| **遵循语言约定** | 遵守编程语言的命名约定 | Java 用 camelCase，Python 用 snake_case |

## 小结

对象-动作-状态哲学为软件中的命名提供了系统化的基础。代码库中的每一个元素都可以被理解为代表一个对象（名词）、一个动作（动词）或一个状态（形容词/名词）。

通过一致地应用这个框架，开发者创建了一门连贯的领域语言，使代码自我文档化且直观。对象根据其类型（实体、值对象、服务）命名。动作根据其性质分类（命令、查询、布尔、转换）。状态根据其类别区分（布尔、枚举、数值、复合）。

这种系统化方法消除了任意的命名决策，创造了一个揭示系统结构和意图的词汇表。结果是代码读起来像自然语言，开发者可以直接从名称中理解关系和职责。

从随意命名到系统化命名的转变，是区分练手项目与专业系统的那些安静但强大的转变之一。
