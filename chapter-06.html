在许多练手项目中，数据一开始是简单而灵活的。开发者可能用字典、列表或松散结构的 JSON 对象来存储信息。这些格式很方便，因为它们允许在不要求严格定义的情况下进行快速实验。

在开发的早期阶段，这种灵活性很有价值。它让想法能够快速从概念变为可运行的代码。

但是，随着项目的增长，这种非正式的数据处理方式开始暴露其局限性。当系统的数据只有松散定义时，整个应用的结构变得不稳定。逻辑散布在多个地方，假设被隐藏起来，变更变得越来越困难。

专业系统通过建立领域模型（domain model）来解决这个问题。

领域模型不仅仅是存储数据的一种方式。它是系统中核心概念及其关系的表征。一旦这些概念被清晰定义，系统的其他部分就可以围绕它们组织起来。

从这个意义上说，领域模型成为了软件的骨架（skeleton of the software）。

7.1 从灵活结构到定义实体（From Flexible Structures to Defined Entities）

练手项目通常将数据视为通用容器。开发者可能像这样存储信息：

一个字典代表一个交易。 一个列表代表任务。 一个 JSON 对象代表用户数据。

这些结构对快速实验来说很好，但它们不能清晰地传达含义。一个字典可能包含许多字段，但没有任何东西明确指出该对象在系统中代表什么。

结果，解释数据的逻辑散布在代码库的不同部分。

领域模型通过引入实体（entities）来解决这个问题——明确定义的、代表系统中有意义概念的对象。

实体是在系统中具有独特身份的东西。它可以随时间变化，但始终代表同一个概念对象。

例如：

  • 一个用户账户
  • 一笔交易
  • 一个任务
  • 一个项目

每个实体代表一个稳定的概念，行为和规则可以围绕它来组织。

一旦引入实体，系统开始以真实概念而非通用容器来描述自己。

7.2 值对象：有意义的属性描述（Value Objects: Describing Attributes with Meaning）

并非系统中所有数据都需要自己的身份。

有些信息只是用来描述实体的属性。这些通常被称为值对象（value objects）。

值对象不代表系统中的独立对象。相反，它代表与实体相关联的有意义的值。

例如，金额、时间戳或地理位置可以作为值对象。它们的重要性不在于身份，而在于它们持有的值。

通过区分实体和值对象，系统获得了清晰度。开发者可以立即理解哪些数据代表核心对象，哪些只是描述这些对象。

这种区分有助于在保持有意义结构的同时防止不必要的复杂性。

7.3 聚合：对相关概念进行分组（Aggregates: Grouping Related Concepts）

随着系统的增长，实体很少孤立存在。它们往往形成必须一起管理的相关对象集群。

聚合（aggregate）就代表这样一个集群。它定义了一个边界，在这个边界内某些实体和值对象紧密交互。

在这个边界内，通常有一个实体作为该组的主要参考点。对相关对象的变更都通过这个中心实体进行，确保系统维护一致的规则。

聚合的目的不是引入抽象理论，而是维持连贯性。通过将相关概念分组在一起，系统防止了分散的逻辑和组件之间的不受控交互。

简单来说，聚合确保相关的数据片段以可预测的方式一起变动。

7.4 数据模型如何塑造系统（How Data Models Shape the System）

一旦领域模型变得清晰，一个有趣的转变就发生了。

许多架构决策开始自然地遵循数据的结构。

如果实体和关系定义良好，存储策略就更容易设计。验证规则变得更清晰。接口开始反映相同的概念结构。甚至用户界面也经常反映底层模型的组织方式。

例如，如果一个系统围绕交易和账户展开，许多功能将自然地以这些实体为中心。接口可能允许用户创建交易、查看账户历史或分析消费模式。

通过这种方式，领域模型不仅影响数据如何存储，还影响整个系统的行为。

当数据模型薄弱或模糊时，软件往往会让人感到支离破碎。当模型强大时，系统获得连贯性。

7.5 软件的骨架（The Skeleton of the Software）

从非正式数据结构到清晰领域模型的转变，标志着项目成熟化的重要一步。

系统不再将数据视为灵活容器的集合，而是开始认识自己的内部概念。实体定义了系统的主要对象。值对象提供了有意义的描述。聚合将相关元素组织成连贯的结构。

这些元素共同构成了软件的骨架。

一旦这个骨架存在，系统的其余部分就可以围绕它以更大的稳定性生长。新功能自然集成，职责更容易分配，系统开始反映它所代表的领域。

没有良好领域模型的系统就像一个没有骨架的生物——它可能暂时存活，但无法承受重量和压力。随着复杂性增加，缺乏结构的数据模型会变得越来越脆弱，难以维护和扩展。

而一个清晰的领域模型为系统提供了坚实的结构基础。就像建筑物的框架一样，它定义了系统的整体形状，并为其他组件提供了附着点。

7.6 实践指南：领域建模步骤

领域建模不是艺术，而是一门可以学习和实践的技艺。

7.6.1 领域建模 SOP

第一步：识别核心概念

  1. 列出系统处理的所有事物
  2. 识别哪些是独立的对象（实体）
  3. 识别哪些是描述性属性（值对象）

第二步：定义关系

  1. 识别概念之间的关系（一对一、一对多、多对多）
  2. 为每个关系命名（如”拥有”、“包含”、“属于”）
  3. 确定关系的方向和基数

第三步：定义聚合

  1. 识别哪些概念总是作为一组被操作
  2. 为每个聚合定义根实体
  3. 确保只有聚合根可以访问聚合内部的其他对象

第四步：验证

  1. 模型是否反映了真实的业务领域？
  2. 是否有遗漏的概念或关系？
  3. 模型是否足够简单以避免过度设计？

7.6.2 实体 vs 值对象：决策树

这个对象需要身份吗？
├─ 是 → 实体（Entity）
│   └─ 它有生命周期吗？
│       ├─ 是 → 实体
│       └─ 否 → 重新考虑是否需要身份
└─ 否 → 值对象（Value Object）
    └─ 它可以被多个实体共享吗？
        ├─ 是 → 值对象
        └─ 否 → 可能是实体

7.6.3 快速诊断：你的数据模型清晰吗？

7.7 小结

领域模型是软件的骨架。它将模糊的数据结构转化为明确定义的概念和关系，为整个系统提供结构基础。

通过实体、值对象和聚合，系统开始反映真实的业务领域。这种反映不仅使代码更易理解，也使系统更稳定、更易维护。

一个好的领域模型不是凭空出现的，它来自于对业务领域的深入理解和持续的重构。它是一个演化的过程，而不是一次性的设计。

下一章，我们将探讨如何组织代码的执行流程。当控制流从条件分支演变为清晰的管道时，系统的可读性和可维护性会如何提升？

实践建议：

  1. 从需求开始：不要直接从数据库表开始建模。先理解业务领域和需求。
  2. 迭代改进：领域模型不需要一次性完美。随着理解的深入，持续改进它。
  3. 使用通用语言：确保技术团队和业务团队使用相同的术语来描述领域概念。
  4. 文档化模型：保持领域模型的文档更新，包括实体图和关系说明。

立即行动：

选择你的项目中的一个核心功能，尝试画出涉及的所有实体和它们的关系。然后，问自己：这个模型是否清晰反映了业务领域？

```
└─ 否 → 值对象（Value Object）
    └─ 它可以被多个实体共享吗？
        ├─ 是 → 值对象
        └─ 否 → 可能是实体
```

### 快速诊断：你的数据模型清晰吗？

- [ ] 你能否在一张图上画出所有核心实体及其关系？
- [ ] 新开发者能否在 30 分钟内理解主要的数据结构？
- [ ] 是否避免了使用通用的字典或列表来表示领域概念？
- [ ] 实体和值对象的区别是否清晰？
- [ ] 聚合边界是否明确定义？

-----------------------------------------------------------------------

## 小结

领域模型是软件的骨架。它将模糊的数据结构转化为明确定义的概念和关系，为整个系统提供结构基础。

通过实体、值对象和聚合，系统开始反映真实的业务领域。这种反映不仅使代码更易理解，也使系统更稳定、更易维护。

一个好的领域模型不是凭空出现的，它来自于对业务领域的深入理解和持续的重构。它是一个演化的过程，而不是一次性的设计。

下一章，我们将探讨如何组织代码的执行流程。当控制流从条件分支演变为清晰的管道时，系统的可读性和可维护性会如何提升？

-----------------------------------------------------------------------

**实践建议：**

1. **从需求开始**：不要直接从数据库表开始建模。先理解业务领域和需求。
2. **迭代改进**：领域模型不需要一次性完美。随着理解的深入，持续改进它。
3. **使用通用语言**：确保技术团队和业务团队使用相同的术语来描述领域概念。
4. **文档化模型**：保持领域模型的文档更新，包括实体图和关系说明。
