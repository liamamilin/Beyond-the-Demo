随着软件的演化，它会累积变更。

功能被添加，错误被修复，行为被改进，有时现有功能被修改。从开发者的角度来看，这些变更是构建和完善系统的自然过程的一部分。

然而，对于用户和协作者来说，除非变更被清晰地传达，否则它们可能是令人困惑的。

专业项目因此将变更本身视为必须被管理和解释的东西。它们引入了使系统演化可见和可理解的机制。

其中最常用的三种机制是版本控制（versioning）、变更日志（changelogs）和发布说明（release notes）。

这些工具共同允许一个项目传达它是如何随时间变化的。

22.1 版本号即信号（Version Numbers as Signals）

版本号不仅仅是贴在发布上的标签。它是一个信号，帮助用户理解他们应该期待什么类型的变更。

专业项目通常遵循一个称为语义化版本（Semantic Versioning，简称 SemVer）的结构化版本方案。

在这个方案中，版本号遵循三部分格式：

MAJOR.MINOR.PATCH（主版本号.次版本号.修订号）

每个部分传达不同级别的变更。

修订号（PATCH）的递增通常表示不改变现有行为的小修复。次版本号（MINOR）的递增引入了新功能，同时保持与以前使用的兼容性。主版本号（MAJOR）的递增表示可能改变现有行为或需要用户调整工作流的重大变更。

因为每个数字的含义是一致的，用户无需阅读整个代码库就可以解读更新的影响。

版本号因此充当了一种语言，项目通过它传达其演化。

22.2 变更日志即历史记录（Changelogs as Historical Records）

虽然版本号提供信号，但它们不描述变更的细节。

这个角色属于变更日志（changelog）。

变更日志是每个发布中引入的变更的结构化记录。它不是迫使用户检查提交历史或代码差异，而是以可读的格式总结重要的更新。

典型条目可能包括新功能、错误修复、性能改进和对现有行为的变更。

通过按版本组织这些条目，变更日志成为了项目开发的历史记录。

用户可以快速回顾系统是如何演化的，并确定新发布是否影响他们的使用。

22.3 发布说明即沟通（Release Notes as Communication）

发布说明通过以对用户有意义的方式组织变更来进一步扩展这个想法。

虽然变更日志可能列出技术更新，但发布说明通常解释为什么这些变更很重要。它们可能突出最重要的改进，描述新能力，或提供关于如何采用更新功能的指导。

从这个意义上说，发布说明不仅仅是技术文档。它们是沟通的一种形式。

它们将内部的开发活动转化为用户能够理解和欣赏的信息。

22.4 建立发布节奏（Establishing a Release Rhythm）

专业软件开发的另一个方面是发布节奏（release rhythm）的概念。

练手项目通常不定期地发布更新。变更累积起来，直到开发者决定发布一个新版本。

专业项目倾向于遵循更可预测的模式。

更新可能按固定时间间隔发布，或者团队可能遵循为重大改进定义的里程碑。即使确切的日程有所变化，项目也会一致地传达其进展。

这种节奏帮助用户理解何时期待改进以及项目被维护的活跃程度。

稳定的发布节奏表明系统是有生命的、正在演化的。

22.5 面向外部世界说话（Speaking to the Outside World）

许多练手项目仍然是面向内部的。开发者理解变更，因为他们写了代码，但项目不向其他人解释自己。

专业系统认识到软件存在于用户、协作者和利益相关者的社区中。

这些受众需要关于系统如何演化的清晰信号。

版本号提供了变更的快速指示。变更日志提供了开发的结构化历史。发布说明将技术更新转化为有意义的沟通。

这些元素共同允许项目面向外部世界说话。

这种清晰地沟通演化的能力是成熟度的一个重要方面。

一个专业项目不会简单地随时间变化。

它以别人能够跟随和信任的方式解释那些变化。

22.6 实践指南：语义化版本发布 SOP

22.6.1 语义化版本规范

版本号格式：MAJOR.MINOR.PATCH

  • MAJOR（主版本号）：当进行不兼容的 API 修改时递增。示例：1.0.0 → 2.0.0
  • MINOR（次版本号）：当添加向后兼容的功能时递增。示例：1.0.0 → 1.1.0
  • PATCH（修订号）：当进行向后兼容的问题修复时递增。示例：1.0.0 → 1.0.1

22.6.2 发布流程 SOP

  1. 变更收集：从上次发布开始收集所有变更，分类为新增/修复/破坏性变更
  2. 版本号决策：检查是否有破坏性变更 → MAJOR；是否有新功能 → MINOR；只有修复 → PATCH
  3. 更新文件：更新版本号、CHANGELOG.md、README.md
  4. 创建发布：创建 Git 标签，构建发布包，发布到包管理器
  5. 发布通知：撰写 Release Notes，通知用户

22.6.3 CHANGELOG 模板

# Changelog

## [1.2.0] - 2024-01-15

### Added
- 新增用户认证功能
- 添加 API 速率限制

### Fixed
- 修复登录超时问题
- 修复数据库连接泄漏

22.7 小结

版本管理不仅是技术实践，更是与用户沟通的方式。通过语义化版本、清晰的 CHANGELOG 和详细的 Release Notes，系统演化变得透明和可理解。

好的版本管理让用户信任系统，知道何时升级、如何升级以及升级会带来什么影响。

立即行动：

为你的项目创建一个 CHANGELOG.md 文件，并制定下次发布的计划。确保你的版本号遵循语义化版本规范。
