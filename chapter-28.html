实用的系统不仅仅由思想构建。它们由可重复的结构（repeatable structures）构建。

以下附录提供了直接可用的模板和速查表，帮助你将一个小项目转化为立即感觉更专业的东西。

这些模板有意保持简洁。它们的目标不是复杂度，而是清晰和一致。

29.1 A. 专业 README 模板（可直接复制）

一个专业的 README 快速回答三个问题：

  1. 这是什么？
  2. 它为什么存在？
  3. 我怎么使用它？

以下是许多成熟项目使用的最小结构：

# 项目名称

一行简短描述。

示例：
一个用自然语言管理个人支出日志的轻量级 CLI 工具。

---

## 功能特性

- 功能 1
- 功能 2
- 功能 3

---

## 安装

```bash
pip install project-name
# or
npm install project-name

29.2 快速开始

project-name init
project-name add "coffee 5"
project-name report

29.3 示例

输入：

add lunch 12

输出：

Expense recorded.
Total today: $12

29.4 配置

环境变量：

PROJECT_DB_PATH
PROJECT_ENV

29.5 架构（可选）

CLI → Service Layer → Storage

29.6 路线图

  • Web 仪表盘
  • 移动端输入
  • 导出报告

29.7 贡献

欢迎 Pull Request。

29.8 许可证

MIT


一个结构化的 README 本身就能极大地改善项目被感知的方式。

## B. 目录结构模板

一个清晰的目录结构能立即传达系统架构。

以下是三种常见的模式。

### Python 项目

project/ ├── src/ │ └── project/ │ ├── init.py │ ├── cli.py │ ├── service/ │ ├── models/ │ └── storage/ ├── tests/ ├── docs/ ├── examples/ ├── pyproject.toml ├── README.md └── LICENSE


核心思想：`src/` 防止导入混淆，`models/` 持有领域实体，`service/` 包含业务逻辑。

### Node.js 项目

project/ ├── src/ │ ├── api/ │ ├── services/ │ ├── models/ │ ├── middleware/ │ └── utils/ ├── tests/ ├── scripts/ ├── package.json ├── README.md └── .env.example


原则：分离 **API**、**逻辑**和**数据模型**。

### Web 应用

project/ ├── frontend/ │ ├── components/ │ ├── pages/ │ ├── hooks/ │ └── styles/ ├── backend/ │ ├── api/ │ ├── services/ │ └── models/ ├── infra/ ├── docs/ └── README.md


原则：分离 **UI**、**逻辑**和**基础设施**。

## C. UI 规则速查表

专业界面遵循一致的视觉规则。

### 字体层级

常见层级：

Title 32px Heading 24px Subheading 18px Body 16px Caption 14px


规则：永远不要随机发明新的字号。

### 间距比例

使用一致的增量。例如：

4 8 16 24 32 48 64


规则：所有边距和内边距都应该来自这个比例。

### 色彩系统

最小调色板示例：

Primary Gray 900 (文字) Gray 700 Gray 500 Gray 300 Gray 100 (背景)

Accent color (强调色) Error color (错误色) Success color (成功色)


规则：大多数 UI 应该使用灰度色。强调色要克制地使用。

### 对齐

始终将元素对齐到网格。避免随机偏移。

### 留白

如果页面感觉杂乱，在添加设计之前先增加间距。

## D. 发布检查清单

在发布之前，专业团队会验证一小套条件。

### 代码
- [ ] 测试通过
- [ ] Lint 通过
- [ ] 没有调试日志

### 文档
- [ ] README 已更新
- [ ] 变更日志已更新
- [ ] 版本号已更新

### 打包
- [ ] 安装命令工作正常
- [ ] 依赖正确

### 安全
- [ ] 机密已移除
- [ ] `.env` 未提交

### 用户体验
- [ ] 空状态工作正常
- [ ] 错误状态工作正常
- [ ] 加载状态工作正常

### 发布
- [ ] Git 标签已创建
- [ ] 发布说明已编写
- [ ] 包已发布

-----------------------------------------------------------------------

## E. "练习品"诊断（10 秒测试）

如果一个项目感觉像练手项目，它通常在以下检查中的几项上失败。

### 结构
- [ ] 项目有清晰的目录结构吗？

### 安装
- [ ] 可以用**一个命令**安装吗？

### 文档
- [ ] README 清晰解释了用法吗？

### 接口
- [ ] 输入和输出可预测吗？

### 可观测性
- [ ] 有日志吗？

### 错误处理
- [ ] 错误状态被干净地处理了吗？

### UI
- [ ] 间距一致吗？

### 发布
- [ ] 有版本号吗？

### 未来
- [ ] 有路线图吗？

### 信任
- [ ] 有提到安全或隐私吗？

### 规则

如果项目在大多数检查上失败，它会**看起来像学习项目**。

如果它通过了大多数检查，它会**看起来像真正的产品**——即使代码库很小。

这就是成熟度信号的力量。

它们改变感知。

而感知往往是简单演示和专业系统之间的区别。

# 附录：模板、速查表与诊断工具（Appendix: Templates, Cheat Sheets & Diagnostic Tools）

实用的系统不仅仅由思想构建。它们由**可重复的结构（repeatable structures）**构建。

以下附录提供了直接可用的模板和速查表，帮助你将一个小项目转化为立即感觉更专业的东西。

这些模板有意保持简洁。它们的目标不是复杂度，而是**清晰和一致**。

-----------------------------------------------------------------------

## A. 专业 README 模板（可直接复制）

一个专业的 README 快速回答三个问题：

1. 这是什么？
2. 它为什么存在？
3. 我怎么使用它？

以下是许多成熟项目使用的最小结构：

30 项目名称

一行简短描述。

示例： 一个用自然语言管理个人支出日志的轻量级 CLI 工具。

30.1 功能特性

  • 功能 1
  • 功能 2
  • 功能 3

30.2 安装

pip install project-name
# or
npm install project-name

30.3 快速开始

project-name init
project-name add "coffee 5"
project-name report

30.4 示例

输入：

add lunch 12

输出：

Expense recorded.
Total today: $12

30.5 配置

环境变量：

PROJECT_DB_PATH
PROJECT_ENV

30.6 架构（可选）

CLI → Service Layer → Storage

30.7 路线图

  • Web 仪表盘
  • 移动端输入
  • 导出报告

30.8 贡献

欢迎 Pull Request。

30.9 许可证

MIT


一个结构化的 README 本身就能极大地改善项目被感知的方式。

-----------------------------------------------------------------------

## B. 目录结构模板

一个清晰的目录结构能立即传达系统架构。

以下是三种常见的模式。

### Python 项目

project/ ├── src/ │ └── project/ │ ├── init.py │ ├── cli.py │ ├── service/ │ ├── models/ │ └── storage/ ├── tests/ ├── docs/ ├── examples/ ├── pyproject.toml ├── README.md └── LICENSE


核心思想：`src/` 防止导入混淆，`models/` 持有领域实体，`service/` 包含业务逻辑。

### Node.js 项目

project/ ├── src/ │ ├── api/ │ ├── services/ │ ├── models/ │ ├── middleware/ │ └── utils/ ├── tests/ ├── scripts/ ├── package.json ├── README.md └── .env.example


原则：分离 **API**、**逻辑**和**数据模型**。

### Web 应用

project/ ├── frontend/ │ ├── components/ │ ├── pages/ │ ├── hooks/ │ └── styles/ ├── backend/ │ ├── api/ │ ├── services/ │ └── models/ ├── infra/ ├── docs/ └── README.md


原则：分离 **UI**、**逻辑**和**基础设施**。

-----------------------------------------------------------------------

## C. UI 规则速查表

专业界面遵循一致的视觉规则。

### 字体层级

常见层级：

Title 32px Heading 24px Subheading 18px Body 16px Caption 14px


规则：永远不要随机发明新的字号。

### 间距比例

使用一致的增量。例如：

4 8 16 24 32 48 64


规则：所有边距和内边距都应该来自这个比例。

### 色彩系统

最小调色板示例：

Primary Gray 900 (文字) Gray 700 Gray 500 Gray 300 Gray 100 (背景)

Accent color (强调色) Error color (错误色) Success color (成功色)


规则：大多数 UI 应该使用灰度色。强调色要克制地使用。

### 对齐

始终将元素对齐到网格。避免随机偏移。

### 留白

如果页面感觉杂乱，在添加设计之前先增加间距。

-----------------------------------------------------------------------

## D. 发布检查清单

在发布之前，专业团队会验证一小套条件。

### 代码
- [ ] 测试通过
- [ ] Lint 通过
- [ ] 没有调试日志

### 文档
- [ ] README 已更新
- [ ] 变更日志已更新
- [ ] 版本号已更新

### 打包
- [ ] 安装命令工作正常
- [ ] 依赖正确

### 安全
- [ ] 机密已移除
- [ ] `.env` 未提交

### 用户体验
- [ ] 空状态工作正常
- [ ] 错误状态工作正常
- [ ] 加载状态工作正常

### 发布
- [ ] Git 标签已创建
- [ ] 发布说明已编写
- [ ] 包已发布

-----------------------------------------------------------------------

## E. "练习品"诊断（10 秒测试）

如果一个项目感觉像练手项目，它通常在以下检查中的几项上失败。

### 结构
- [ ] 项目有清晰的目录结构吗？

### 安装
- [ ] 可以用**一个命令**安装吗？

### 文档
- [ ] README 清晰解释了用法吗？

### 接口
- [ ] 输入和输出可预测吗？

### 可观测性
- [ ] 有日志吗？

### 错误处理
- [ ] 错误状态被干净地处理了吗？

### UI
- [ ] 间距一致吗？

### 发布
- [ ] 有版本号吗？

### 未来
- [ ] 有路线图吗？

### 信任
- [ ] 有提到安全或隐私吗？

### 规则

如果项目在大多数检查上失败，它会**看起来像学习项目**。

如果它通过了大多数检查，它会**看起来像真正的产品**——即使代码库很小。

这就是成熟度信号的力量。

它们改变感知。

而感知往往是简单演示和专业系统之间的区别。
